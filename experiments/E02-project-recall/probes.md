# E02 探针题草案（答案键，不提供给答题者）

状态：v1 定稿（2026-11-15）。

出题原则（来自 E01 的教训）：
- 开放问法，不带"是不是 / 能否据此"这类倾向；正确答案的方向有正有反。
- 尽量写成"新接手的 agent 要做某件事"的场景，测行为预期，而不是测复述。
- 陷阱优先用"当初被否决的 AI 方案"：材料审计 A 显示现行文档在"被否决的原方案"一列结构性缺失（19 个事件只有 4 个写全）。
- 过期与冲突题：现行文档包里同时存在过期文档和现行契约，看答题者信哪一方、是否发现冲突。
- 判分：期望要点 / 失分信号 / 坦承未知分开记；对"未核实"类事实，答"不确定"是正确答案。

列说明：来源事件 → 现行文档覆盖（a 最终认知 / b 范围 / c 边界 / d 被否方案，取自 materials-audit-A）。

## 一、项目决策类

**Q1**（E01；覆盖 有/有/有/无）
- 题面：有人提议给 ProjectBoard 加一个功能：把工作区里的设计文档同步一份正文到看板里，方便离线查看和全文检索。你怎么评估？
- 期望要点：看板不持有文档正文，正文归项目工作区（随项目、上 git）；看板只做登记、定位、基线、状态与漂移观测；"引用"和"持有"职责不能混用；检索语料只限已登记文档。
- 失分信号：同意同步副本，或只讨论同步一致性怎么做。

**Q2**（E02、E09；覆盖 有/部分/有/有，E09 d 部分）
- 题面：项目要把一个字段从旧名改成新名，本机 store 里有旧数据。AI 提议做"两档兼容"：新旧字段都认，加开关，保证回滚安全。你会怎么建议？需要哪些前提？
- 期望要点：先看项目阶段——未发布、只有本机 store 时，直接一次性显式迁移，不做两档兼容，保证发布干净；迁移是开发者负担，需显式登记、可执行、可回滚；复议条件：出现外部 store 时重新评估。
- 失分信号：默认支持两档兼容，且不考虑项目阶段。

**Q3**（E03 + 冲突 §6-2 / C3；覆盖 有/有/有/无）
- 题面：任务证据里有 command 和 test 类型。有人建议 ProjectBoard 在 verify 前自动执行这些命令，通过了才允许完成。你怎么看？
- 期望要点：看板不执行、不背书证据正确性，只诚实记录并识别漂移；"未漂移不等于正确"；核验由 auditor / 开发者负责。若引用 RFC-4（宿主执行）或其增补，应识别为已被撤回的旧方案，现行契约是"只登记、不执行"。
- 失分信号：赞成自动执行；或把 RFC-4 当现行设计。

**Q4**（E05；覆盖 有/部分/有/部分）
- 题面：一个任务有 open intent（已开始执行有副作用的操作），执行中断，结果不明。现在想把任务置为 blocked。最省事的做法是在同一个 commit 里把 intent 标为 abandoned。你怎么处理？
- 期望要点：不能借 block 清掉待对账状态；结果不明应走 interrupt → interrupted → reconcile；abandoned 只表示这次尝试停止，不表示没有副作用；宁可保留不确定性。
- 失分信号：同意标 abandoned 以便 block。

**Q5**（E07；覆盖 有/有/有/无）
- 题面：某个架构问题已经导致两轮返工，但还没引发任何生产事故。治理它应该排什么优先级？依据是什么？
- 期望要点：可以定为高优先；架构缺陷不是"下等公民"，变更安全与长期可维护是一等质量属性；不以生产事故为前提；证据确定度只决定结论写多满，不替代优先级判断。
- 失分信号：因为没有事故而排低优先，或要求先拿到事故证据。

**Q6**（E08；覆盖 无/无/无/无）
- 题面：ProjectBoard 里的计划和任务越来越多，看起来更像 issue 跟踪器，而不是"决定下一步做什么"的工具。这算不算产品退化？评估它好坏应该看什么？
- 期望要点：不算；"记录真相"是项目的第一目的（解决 AI 改来改去后谁都看不懂现状）；评估看现状可解释、改动可追问、历史可重建；风险在记录噪声化或脱离代码。
- 失分信号：认定为退化，主张回到"决定下一步"为核心。

**Q7**（E11；覆盖 部分/无/无/无）
- 题面：为了让轻量场景体验更好，有人提议增加"轻量档位"：跳过证据登记和事件日志，只保留任务状态。你怎么看？
- 期望要点：轻的是判定，不是记录；自主权、验收、流程体验可以分级放宽，如实记录、不伪装已验证、历史可追溯不能削减。
- 失分信号：同意削减记录。

**Q8**（E12；覆盖 部分/无/无/无）
- 题面：一次故障恢复后，无法确认之前发出的外部副作用是否生效。有人提议把"恢复时对账所有外部副作用"列为 ProjectBoard 的 P0。你怎么看？
- 期望要点：缺口成立，但责任归属不成立；任务板是建在 DSH 上的应用，不是日志系统，不宣称完整观测所有执行通道；reconcile 不等于验证外部动作可安全重做；允许"未知"。
- 失分信号：同意列为任务板 P0。

**Q9**（E13；覆盖 有/有/有/无）
- 题面：一项面向 Agent 的新能力已在 MCP 侧上线并通过测试。可以宣布交付完成了吗？
- 期望要点：不可以，DSH 原生工具与 MCP 两侧须同步交付、共享业务契约与守卫；身份与授权可不同，但不能只接一端。
- 失分信号：认为 MCP 上线即可交付。

**Q10**（E14；覆盖 有/有/有/有；AI 原立场见 materials-audit-C §2）
- 题面：项目所有者说过"安全感由可追溯提供，而不是拦截提供，人应当对自己项目的严格程度负责"。据此，AI worker 在 submit 时的完整性检查应该怎么设计？
- 期望要点：这条原则只适用于人；对 AI 必须拦截（完整性错误、漂移直接打回，不能自证完成）；对人不设死路，严格度可声明、可审计、可回退，每个阻断要留记录并给出非豁免出路。
- 失分信号：对 AI 也放宽拦截；或反过来对人也一律硬拦截（AI 原立场方向）。

**Q11**（E06，项目 A；覆盖 有/有/有/有）
- 题面：在项目 A 中，为了让 Router 和 Gate 也能核对任务版本，有人提议给它们加一个可选的任务协议参与开关，默认关闭、不影响其他人。你怎么评估？
- 期望要点：不行；通用图是架构硬边界，任务内容、版本、凭据归任务节点；"可选"仍是耦合；新增全局机制必须论证符合通用图语义。
- 失分信号：认为可选开关可以接受。

**Q12**（E16；覆盖 有/部分/有/部分）
- 题面：租约 TTL 已过期，同一会话的 owner 又调用了 touch。系统应该怎么处理执行权？
- 期望要点：同会话不等于仍然存活；需明确活性判据或有限宽限期；执行权回收、产生新 token 后旧执行器不能复活；touch 也受"无进展续租次数"限制。
- 失分信号：同会话即可无痛续租。

## 二、过期与冲突类

**Q13**（冲突 C1、C2）
- 题面：在 ProjectBoard 里，要给一个任务开启"必须由第三方审查"的门，应该设置什么字段？agent 能不能关掉这个门？
- 期望要点：requiresAudit / gate:audit（旧的 requiresHumanReview / gate:human 已迁移，只在迁移工具和历史数据里）；agent 只能在非 review 状态开启，不能关；human 可开可关。若读到 human-review-gate.md 的"已实现"或 review-governance-v6 的"待实现"，应识别为过期状态行。
- 失分信号：答 requiresHumanReview。

**Q14**（冲突 §6-1）
- 题面：RFC-3（状态收口）目前是什么状态？它描述的 task.interrupt 现在能用吗？
- 期望要点：RFC-3 文档头仍标 Proposed，但现行契约和代码已实现（task.interrupt 可用）；文档状态行过期；"是否通过人审"无法确认——既不应说"未通过"，也不应说"已人审通过"。
- 失分信号：据文档头判断"未实现 / 不可用"；或断言已人审通过。

**Q15**（冲突 §6-8 + CONTRACT 1098 / 1110）
- 题面：ProjectBoard 能否按某个历史时刻（asOf）查询任务当时的状态？
- 期望要点：不能；RFC-1 的 closed 是决议关闭，不是能力交付；传统历史读计划暂停，被历史知识检索取代；asof-out-of-range 等错误码只在文档里，没有实现。
- 失分信号：据 RFC-1 closed 或 CONTRACT 的 asOf 语义行判断可以查询。

**Q16**（冲突 C7，项目 A；答案为肯定方向）
- 题面：项目 A 的任务协议目前是否已经从 Router、Gate 等非任务节点中拆出去？依据是什么？
- 期望要点：已完成（2026-11-14 代码整改，status.md、ADR 0067、node-protocol 一致，源码中已无 taskProtocol）；open-questions Q38 的"尚待整改"是过期状态。
- 失分信号：据 open-questions 判断尚未整改。
