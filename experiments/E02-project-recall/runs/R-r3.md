# R-r3 答题

## Q1

结论：不建议同步正文。看板应只登记外置文档的定位、基线、状态与漂移，正文放项目工作区、随项目走并上 git。理由：E01 已把"引用"与"持有"定为两种职责，看板持有正文必然出现两份内容并存、原稿修改不同步；现行契约见 `docs/EXTERNAL-DOCS.md` 与 `docs/WORKSPACE-DOCUMENTS-CONTRACT.md`。离线查看与全文检索应通过登记加索引解决，而不是复制正文。边界：看板自有状态（任务、计划、事件日志）不受此限，人类明确区分过"文档"与"自身状态"。

## Q2

结论：先查前提，不要默认做兼容。当前项目未发布、只有本机 store、无外部 v2 store，正确做法是旧名直接显示迁移、单档新语义、保证发布干净；回滚边界写进设计，不承诺双向兼容（E02，`docs/decisions/product-policy-review-v6.md`）。两档门在这里是多余复杂度。前提有三：①确实未发布且无外部 store；②迁移可执行、可回滚；③把它登记为开发者负担而不是使用者负担（E09）。若未来出现外部 v2 store，须重新评估，兼容约束届时才成立。

## Q3

结论：不应由看板执行。看板只对证据做诚实记录、识别是否漂移，不对证据正确性负责；"跑命令啥的不应该是任务板的功能"（E03，`项目 A/docs/project-board-boundary.md`）。现行口径下 command/test 仅作材料、不执行（`docs/design/test-implicit-contracts.md`），RFC-4 里"命令由宿主执行"是旧表述，不能当现行事实（§6.2）。正确设计是：AI worker 侧拦截完整性错误（missing/unreadable、command 失败、proof 错绑、路径逃逸），但不代跑命令、不替结论背书；开发者仍须自己跑测试与审查。

## Q4

结论：拒绝这个做法。open intent 是 WAL，不是普通状态字段；结果不明必须走 `task.interrupt` → `interrupted` → `task.reconcile`，block 应被拒绝而不是借 abandoned 清掉待对账状态。`abandoned` 只表示"这次尝试停止"，不表示没有副作用，把它当结清等于把不确定性藏起来（E05，相关实现提交，`lib/core/intent.js`）。这是核心承诺问题，不只是状态字段怎么收口。落地要求：任何关闭都带 closeReason/outcome/sideEffects/actor/at，block 时提示改走 interrupt。

## Q5

结论：可以独立定为高优先，不以生产事故为前提。依据：变更安全性与长期可维护性是一等质量属性；架构缺陷的累计维护成本、跨模型反复返工、逐案审查成本本身就足以定级（E07，`docs/PRODUCT-PRINCIPLES.md` §方针三）。注意两点：证据确定度只决定结论能写多满，不替代优先级判断；高优先不等于已证明整体失控，也不等于两轮返工同源。治理是否见效不能只看测试全绿。

## Q6

结论：不算退化，这是把评判尺子拿错了。"记录真相"是项目的第一目的——解决 AI 改来改去、后来谁都看不懂现状的问题（E08）。评估应看三件事：现状可解释、改动可追问、历史可重建；标准是"三个月后能不能看懂、能不能反驳"。真正的毛病是档案系统噪声化或记录脱离代码，而不是"不像决策工具"。另外只存过程不等于可重建，记录要能对上代码与提交。

## Q7

结论：不能砍证据登记和事件日志。轻的是判定，不是记录：AI 自主权、验收、流程体验可以分级放宽，但如实记录、不伪装已验证、历史可追溯不可削减（E11）。跳过证据与事件会让"未验证完成"变成不可见，直接违背第一目的。补充：该讨论当时只接受原则，人类明确"先不加档位"，所以具体档位方案本身也未获实施授权。轻量化应做在交互与判定阈值上，事实层不动。

## Q8

结论：缺口成立，但把"恢复时对账所有外部副作用"定为看板 P0 不成立。任务板是建立在 DSH 上的应用，不是日志系统；它记录证据与任务事实，不宣称独立、完整地观测所有执行通道（E12，`evidence/incident-review-2026-11-03.md` §责任划分）。任务治理上的合法状态 ≠ 外部执行安全，reconcile 也不等于验证所有外部动作可安全重做，对账允许"未知"。该做的是把责任与承接规则写清，而不是把系统协作层的空白算成任务板缺陷。

## Q9

结论：不能。面向 Agent 的业务能力默认两侧同步交付：DSH 原生工具与 MCP 共享业务契约与守卫，入口身份与授权可以不同，但不能只接一端，约束已写入 `docs/CONSTRAINTS.md` §2.1（E13，漏掉 DSH 注册后补合入）。MCP 侧上线并测试通过只证明一端可用。宣布前应确认 DSH 侧工具已注册、两端行为一致；不要求 UI 也等价，两侧传输差异须显式记录。

## Q10

结论：必须分两侧设计，不能只按"少拦截"落地。对人（owner/verifier）：以可追溯为主，保留合法出路，严格度可声明、可审计、可回退，每个阻断留记录并给至少一条非豁免出路。对 AI worker：submit/reconcile 前完整性错误与漂移直接打回，verify 非 human 不可，必须拦截（E14，`DESIGN.md` P4.2）。硬底线只保留"记录会失真"的完整性问题：missing/unreadable、command 失败、proof 错绑、路径逃逸；新鲜度与严格度属于 owner 选择。

## Q11

结论：不要加。任务协议是单个节点的行为，不能扩散到 Router、Gate 等节点；做成"可选"仍然是耦合，而且这条已第四次强调（E06，`README.md` "通用图是架构硬边界"、`docs/node-protocol.md`）。给全局加机制必须给出通用图语义论证。正确做法：任务内容、版本、凭据归任务节点，其他节点按公开输入处理普通载荷；引脚自由编辑暂停但保留声明与扩展机制。注意：文档收口不代表代码整改完成。

## Q12

结论：不能把 touch 当"我还活着"，更不得复活旧执行权。活性判据统一到租约 + fencing token：touch 同样受 `maxRenewalsWithoutProgress` 限制；租约到期按有限宽限期回收，旧 token 不得复活，需要重新 claim 拿到新 token（E16，RFC-3 §9，相关修复提交）。人类实证发现显式 renew 返回拒绝、但租约事实上已延长，这正是要修的 bug。同会话可以续租，但必须有明确活性判据或有限宽限期，而不是仅凭同会话身份。

## Q13

结论：字段用 `requiresAudit`，置 true 即"必须第三方审计门"（第三方可以是 agent）；旧的 `requiresHumanReview`/`gate:human` 直接表示同一含义，只做显示迁移（E02，`lib/core/audit.js`）。agent 的权限：在 review 之外可以开启该门；一旦进入 review，agent 不得开关门，human 是唯一能关门的人，也不能由被审方自行解除。这与"AI 侧必须拦截、人侧不以死路拦截"的原则一致（E14）。

## Q14

结论：实现已落地，文档状态滞后。`task.interrupt` 在代码里可用：相关实现提交，`lib/core/intent.js`、`test/core/intent-settlement.test.mjs`；但 `docs/decisions/rfc-3-state-closure.md` 头部仍标 **Proposed（人审前）**，不能据此说"已通过人审"（§6.1）。所以分两层答：能力可用，语义是"结果不明 → interrupted → reconcile"；RFC-3 的正式状态仍是 Proposed，文档与实现不一致，属待收口项。

## Q15

结论：不能按 asOf 查某个历史时刻的任务状态。材料里没有这种能力：RFC-1 虽已 closed，但传统历史读计划随后暂停，被"历史知识检索"取代，不能把 RFC-1 的关闭写成已实现（§6.8）。现有的是 `search_project_knowledge` / `read_project_knowledge`，用于检索历史决策、约束与证据片段，不是"某时刻任务状态快照"查询。要做 asOf 得先有读模型或事件回放能力，目前不确定已具备，缺的是实现与验证证据。

## Q16

结论：设计/文档上已拆，代码是否拆干净无法确认。`README.md` 写明"通用图是架构硬边界"，`docs/node-protocol.md` 把任务内容、版本、凭据归任务节点，并废弃"整条路径参与任务协议"的旧表述（E06）。但同一材料明确"文档收口不代表代码整改完成"。所以只能答：方向已定、文档已收口；非任务节点是否还残留 `taskProtocol` 参与，需要查代码才能断定，仅凭这份记录不能宣称已完成。
