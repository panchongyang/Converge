# E02 项目回忆 — B0-r3

说明：本次作答未读取、搜索或列出任何项目文件，也未执行命令或联网；仅凭题目描述、ProjectBoard/项目 A 的工具语义（schema 中的行为约定）与一般工程判断。凡涉及项目内部事实（RFC 状态、模块是否已拆分）的，一律标为不确定并说明缺什么。

## Q1

结论：不建议做，最多做"引用 + 带哈希的本地缓存"。

理由：ProjectBoard 的文档模型是"登记工作区文件的位置，不搬运正文"——外部文档只登记 locator，正文留在 git 里，内联文档是只读档案。同步正文会立刻制造第二个真相源：文档改了看板不知道，看板里检索到的还是旧版本。真正的痛点是离线与全文检索，应该用索引解决（检索回源读文件，缓存只做加速并附内容哈希与来源 commit），而不是复制正文。若一定要落正文，必须标注它不可作为评审依据。

## Q2

结论：优先一次性迁移，反对"双档兼容 + 开关"。

双档兼容的代价不是多两行 if，而是测试矩阵翻倍、开关永久化，以及"新旧都写"时的不一致。可行形态只有一种单向兼容：读旧写新，迁移一次性且幂等，代码不允许回写旧字段。前提有四条：store 是单写者；旧数据可重建或有备份；迁移可重跑；回滚靠"新代码读旧数据"而不是"旧代码读新数据"。还要确认外部消费方（其他 agent / MCP 客户端）是否也读这个字段——有外部读者时先加版本字段再迁。

## Q3

结论：不要。

ProjectBoard 对 verify 的定位是"记录验收，不是验证正确性"，报告是自我声明，看板不执行证据命令。把 command/test 改成 verify 前自动执行，等于让任务描述成为任意代码执行入口，还要在看板进程里承担沙箱、依赖、环境差异和 flaky test 的后果；执行失败时也分不清是环境问题还是实现问题。合理分工：证据仍由提交方声明并附结果/哈希，执行放在独立 runner 或 CI，看板只登记"谁在什么环境跑过、结果如何"。需要强制时用审计门，不用自动执行。

## Q4

结论：不能在同一 commit 里把 intent 标成 abandoned。

"结果不明"是事实状态，abandoned 是对事实的断言，两者不能互换。正确顺序是：先 interrupt 关闭开放 intent 并记录已观察到的副作用，再 reconcile 去外部核对实际发生了什么，最后才 block。block 时若仍有开放 intent，必须带 intent:{outcome:"stopped", sideEffects:[...]}，否则审计链就断了。省下的一次提交，换来的是以后永远无法回答"这个副作用到底发生过没有"。

## Q5

结论：按 P1 排，插在新功能之前，但不必升到 P0。

依据不是"有没有事故"，而是"已经付出的代价"：同一架构问题导致两轮返工，说明它不是理论风险而是稳定复现的成本，第三轮几乎必然发生，越晚改越贵。没有生产事故只说明当前负载和路径还没踩到，不构成低优先级证据。做法上把它限定成有验收标准的小重构（明确"改完哪两件事不再返工"），而不是无限期的架构治理；改完用返工次数和改动半径验证效果。

## Q6

结论：不算退化，但要看它是否守住了"决策面"。

任务变多是使用深入的自然结果；退化发生在录入不再经过决定——任何想法都能进看板、没有 WIP 上限、没有 focus、没有验收标准的卡片堆积。评估看四个指标：从"出现新信息"到"决定下一步"的时延、WIP 与并行度、无 owner/无验收标准的任务占比、以及新条目是否绑定到某个计划步骤。这些还健康，它只是同时承担了记录职能；如果决策时延在涨，就该把记录层和决策层分开（计划/步骤管决定，任务只管执行）。

## Q7

结论：不要把"跳过证据和事件"做成同一看板里的档位。

证据登记和事件日志是 ProjectBoard 可追溯性的全部来源。砍掉它们，剩下的状态机无法回答"谁在什么时候基于什么把它标成完成"，而这正是它相对 todo list 的价值。更麻烦的是混档：同一块板上有的任务可审计、有的不可，审计门和统计都会失真。轻量诉求应用别的手段满足：更少的必填字段、模板化提交，或在看板之外用个人清单；若确实要档位，必须显式标注，且禁止升档后直接进入审计门。

## Q8

结论：方向对，但"对账所有外部副作用"作为 P0 不可实现，会把 P0 变成永久承诺。

看板不拥有外部系统，也无法观察它们；"所有"没有边界，等于要求每个集成都实现查询与幂等。可落地的是把 P0 收紧为机制：每个副作用在发出前登记幂等键与可查询句柄，恢复时只枚举"结果不明"的 intent 逐个 reconcile，且 reconcile 必须有明确的三态结果。覆盖面扩大是 P1/P2 的持续工作。先承诺"不确定的能被找出来并核对"，再谈"全部"。

## Q9

结论：不能，除非"交付"被明确定义为"MCP 侧接口可用"。

MCP 侧测试通过只证明协议、schema、参数校验这一层。交付还差：真实 agent 端到端调用、权限与审批路径、配置与重启生效、对既有会话的向后兼容、文档与已知限制。任何一项没验，用户第一次用就会踩到。建议表述为"MCP 侧已上线，待端到端验收"，并列出验收清单；也不要用 curl 路由或版本号代替真实验证。

## Q10

结论：submit 的完整性检查应是"记录 + 告警 + 可覆盖"，硬失败只留给结构非法。

按这位所有者的取向，安全来自事后可追溯，所以检查应把事实盖在提交上：必填字段缺失、证据指向的文件不存在、哈希对不上、claim 后无 begin 等，都以警告写入提交记录，并允许提交者带理由越过，越过动作本身成为可审计事件。真正该拒绝的只有无法解析、无法入库的数据。严格程度由项目所有者按项目配置（例如是否要求 audit），不由 worker 临时加码，worker 也不能悄悄替人补证据。

## Q11

结论：反对"默认关闭的参与开关"，支持"结构性不参与"。

默认关闭的开关仍是耦合：Router/Gate 代码里出现任务协议分支，就有了两套路径、两倍测试和"打开试试"的诱惑，而这正是要拆掉的东西。若 Router/Gate 只需要版本号，就让任务节点把版本当普通数据传下去，或定义一个极窄的查询接口由组合层注入适配器；Router/Gate 核心不 import 任务协议。判断标准很简单：删掉任务协议包，Router/Gate 是否还能编译并通过测试。能，才算真拆开。

## Q12

结论：touch 必须失败，执行权不因 touch 恢复。

TTL 过期即租约失效，fencing token 随之作废。此时任务可能已被他人 claim，任何用旧 token 的写入都必须被拒绝，否则就是典型的双写。正确路径是重新 claim（若仍空闲）并拿到新的 token 与更高的租约代次，而不是"续一下"。另外 renewal 本身有上限（无进展时最多两次），所以即便没过期，盲 touch 也不该被当成推进。系统应把过期后的 touch 记为一次被拒事件，便于发现卡死任务。

## Q13

结论：字段是 requiresAudit=true（在 gate/create/update 时设置）；agent 不能关。

开启后任务进入"需第三方审查"，verify 需要独立 agent 出具 audit.report（约 20–4000 字），普通自我 verify 不放行。权限上明确：agent 只能在非 review 状态下开启，开启与关闭的最终权力在人（human may enable/disable），也就是 agent 无法自己把门拆掉。设计意图是让"严格"成为项目所有者可配置、且不可被被审对象单方面撤销的东西。

## Q14

结论：不确定。RFC-3 的具体状态我无法确认；task.interrupt 这个操作本身在当前工具面上是可用的（作为 op=interrupt，带 sideEffects 与 intent 处置），但"RFC-3 是否已 adopted、实现到什么程度"必须看仓库里的 RFC 索引与决策记录。

缺什么：RFC 文档本身及其状态字段、对应实现与测试的链接。把"这个 op 存在"当成"RFC-3 已落地"是两件事，不能混。

## Q15

结论：没有一等公民的 asOf 查询，只能近似重建。

从工具面看，project_board / project_task 都只返回当前状态（view=task 需要当前 rev），没有时间参数；能拿到的历史是事件流（view=events，默认 50 条、可调 limit）和文档的固定版本（get_fixed 按 commit 取字节）。所以"当时的状态"要用事件回放重建，且受限于事件保留窗口、事件是否带完整快照、以及时钟来源。要精确回答，需先确认事件是否 append-only 且含状态快照；不确定处在此。

## Q16

结论：不确定，无法确认是否已拆出。

我没有读到 项目 A 的模块结构。间接线索只有 Q11 的提议本身：如果还需要"给 Router/Gate 加任务协议参与开关"，说明版本核对能力尚未以共享接口的形式到达这两个节点——但这既可能是"已拆出、只是没接入"，也可能是"仍然耦合"，不能据此定论。

缺什么：包/模块依赖图、Router 与 Gate 的 import 列表、是否存在独立的任务协议包。可判定标准：移除任务协议依赖后，Router/Gate 仍能编译并通过自身测试。
