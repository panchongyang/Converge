# R-r1

## Q1

结论：不应做"同步一份正文到看板"。ProjectBoard 的既定方向是"项目板不持有文档"：文档正文归项目工作区（自由管理、跟项目走、上 git），看板只保存登记、定位、基线、状态与漂移观测（E01，2026-11-01 15:46 人类表述的目标形态：项目板不持有文档，但能引用并管理文档现状）。

理由：doc.put 式的"拷贝正文"正是 E01 被否决的形态——它是拷贝，别处的原稿修改不会同步，必然出现两份内容并存，而看板的职责是记录与识别漂移，不是持有内容。离线查看/全文检索的诉求应由工作区文件 + 登记引用满足，如需索引也是索引登记文档，不是复制正文。

边界：迁移期可兼容读取内嵌文档（docs/EXTERNAL-DOCS.md §1）；看板自有状态（任务、计划、事件日志）不受此限。若确有离线需求，应先说明为什么工作区 git 副本不够。

## Q2

结论：建议不做"两档兼容"，直接显式迁移到新名，并把回滚边界写进设计。前提是确认项目未发布、只有本机 store、无外部 v2 store。

理由：这正是 E02 的拍板——"旧门直接降级，做显示迁移，因为当前项目未发布，确保发布是干净的"（2026-11-02 22:19）。AI 当时主张"两档门（推荐）"，人类用项目阶段事实否决：未发布时"回滚兼容/存量语义不变"不是真约束，为它付双读成本会把发布弄脏。

前提清单：① 项目未发布且无外部 store（若出现外部 v2 store，需重新评估，见 E02 复议条件）；② 迁移是显式的显示迁移，不做静默降级；③ 回滚边界写明（回滚到旧代码按旧语义处理，不承诺双向兼容）；④ wire 名可保留，改显示与语义即可。

## Q3

结论：不应由 ProjectBoard 在 verify 前自动执行 command/test。

理由：E03 人类明确划定"项目板不应当对证据的正确性负责，它应当只对证据做诚实记录，并能识别出是否漂移。推论：跑命令啥的不应该是任务板的功能"（2026-11-05 19:03）。系统能做（能跑命令、能看 git）不等于产品该做；记录谁在何时提交了什么、来源、是否漂移即可，不判断结论对错。

边界：auditor 可以自行核验并出报告，但"不自动核验/背书"限定于系统职责；证据漂移可识别，但"未漂移不等于正确"。另外现行口径 command/test 仅作材料、不执行（§6 第 2 条指出 RFC-4 旧描述"宿主执行"与现行测试设计冲突，不能当现行事实）。开发者仍须跑测试、独立审查。

## Q4

结论：不能在同一 commit 把 intent 标 abandoned 来让 block 成功。应拒绝 block，走 task.interrupt → interrupted → task.reconcile。

理由：E05 人类判据"副作用结果不明：必须走 interrupted/reconcile，不能借 block 清掉待对账状态"，并补"这是核心承诺问题…宁可保留不确定性，也不能为了满足 I6 把不确定性藏起来"（2026-10-28 00:14）。AI 原方案"A（推荐）：block 成功，并在同一 commit 把 intent 标 abandoned"被否——它让不变量成立，代价是把可能已发生的副作用标成"这次尝试停止"。

实现口径：open intent 是 WAL，不是普通状态字段；关闭必须带结算记录（closeReason/outcome/sideEffects/actor/at）。若确实要中断，用 task.interrupt 记录已观察到的 sideEffects，结果未知的用 outcome=unknown，再由 reconcile 对账。abandoned 只表示本次尝试停止，不表示没有副作用。

## Q5

结论：应列为高优先治理，不以"没有生产事故"为门槛。

理由：E07 人类表态"我个人强烈不同意架构缺陷或者代码缺陷是下等公民"，AI 随即承认"我前面把'治理优先级'过度绑定到生产事故证据，确实把门槛设偏了"（2026-11-08 01:26–01:31）。依据是累计维护成本、跨模型反复返工、逐案审查成本；变更安全性与长期可维护性是一等质量属性。

边界：高优先不等于已证明整体失控，也不等于所有返工同源；证据确定度只决定结论能写多满，不替代优先级判断；治理是否见效不能只看测试全绿。已冻结写入 docs/PRODUCT-PRINCIPLES.md §方针三，但不代表治理完成。

## Q6

结论：不算退化。"记录真相"本身就是这个项目的第一目的。

理由：E08 人类改判"其实记录真相，是我做这个项目的第一目的，为了解决持续推进过程中AI改来改去然后后面谁都看不懂现状是啥"（2026-10-22 23:21）。AI 原先把"决定下一步→记录真相"称作退化，被纠正后换评判体系："那这就不是 issue 中心的毛病，是档案系统的毛病…只比'三个月后能不能看懂、能不能反驳'"。

评估标准三条：现状可解释、改动可追问、历史可重建。不追求"今天推得多快"。边界：只存过程不等于可重建，记录可能噪声化或脱离代码，仍要防。

## Q7

结论：不行。可以轻化判定与交互，不能砍掉如实记录与事件日志。

理由：E11 人类【转述】说明很多时候轻一点好，但不代表幕后工作可以省；可扩大 AI 自主权、放宽验收、把流程体验分级轻量化，但幕后如实记录不能少。AI 接上后归纳为"轻的是判定，不是记录"（2026-11-01 16:21）。砍掉证据登记与事件日志会同时破坏 E08 的"历史可重建"与 E14 的"追溯优先"。

可放宽的：AI 自主权范围、验收严格度、流程档位（分级可调）。不可削的：如实记录、不伪装已验证、历史可追溯。另注意该讨论当时明确"先不加档位，我记住这个就行"——原则被接受，具体档位未获实施授权。

## Q8

结论：缺口成立，但"作为 ProjectBoard 的 P0"责任归属不成立。

理由：E12 AI 起初主张最优先应补"恢复时必须对账"；人类指出这可能是不该在任务板实现的功能，任务板是建立在 DSH 上的应用，而不是日志系统；AI 承认缺口成立、责任归属并不成立（2026-11-03 19:32–19:33）。任务治理上的合法状态 ≠ 外部执行安全；任务板记录证据与任务事实，不宣称独立完整观测所有执行通道；reconcile 也不等于验证全部外部动作可安全重做。

边界：对账允许"未知"；不把系统协作层的责任空白直接归为任务板缺陷。若要立项，应先明确承担方（DSH/宿主层）与任务板只做记录的部分。

## Q9

结论：不能。必须确认 DSH 原生工具侧也已注册、两侧契约一致。

理由：E13 的原始失误是 AI 只报告两个工具已上线、部署任务留在 review，实际只覆盖 MCP 一侧；人类实测发现 DSH 侧没有工具，要求做成两边一致；AI 承认漏了 DSH 的原生工具注册，上一版只接通 MCP（2026-11-14 01:45–01:47）。约束已写入 docs/CONSTRAINTS.md §2.1：面向 Agent 的业务能力默认两侧同步交付、共享业务契约与守卫。

边界：不要求 UI 等价；身份、项目归属沿用各自授权；两侧传输差异须显式记录。MCP 侧测试通过不构成交付完成的证据。

## Q10

结论：AI worker 侧必须拦截，人类那句原则只适用于人。

理由：E14 人类同一分钟内补齐"当然我说的是对人来说，ai确实得拦截"（2026-11-01 22:40）。P4.2 分两侧：AI 侧保留完整性拦截与"不能自证完成"——submit/reconcile 前完整性错误与漂移直接打回，verify 非 human 不可；人侧不以死路拦截，严格度可声明、可审计、可回退，每个阻断留记录并给至少一条非豁免出路。

硬底线只保留"记录会失真"的完整性问题：missing/unreadable、command 失败、proof 错绑、路径逃逸。新鲜度与严格度属 owner 选择，可放宽；但放宽不等于不记录。

## Q11

结论：不该加。"可选参与"仍然是耦合，应保持任务协议是单个节点的行为。

理由：E06 人类第四次强调，任务协议已经耦合，应归为单独节点行为，不要扩展到多个节点；给全局加东西必须说明是否违背通用图。AI 承认实现里把 taskProtocol 加到 Agent、Router、Gate、Join、Human 上，做成"可选"仍然是耦合，之前处理错了（2026-11-13 20:55）。默认关闭并不可豁免架构审查：通用图是架构硬边界，新增全局机制必须给出通用图语义论证。

正确做法：任务内容/版本/凭据归任务节点；Router、Gate 按公开输入处理普通载荷；若要核对版本，通过节点间公开的普通载荷或由任务节点自身行为承担，而不是给多个节点挂协议开关。

## Q12

结论：不能靠 touch 复活执行权；租约到期后按宽限回收，旧 fencing token 作废。

理由：E16。AI 原主张"TTL 过期后 owner 同会话可无痛续租"被否，人类要求"同会话续租可以支持，但必须有明确的活性判据或有限宽限期"（2026-10-28 00:14）；后又实证"显式 renew 虽然返回拒绝，租约事实上已经延长"（13:05），促成统一 touch/renew/自动重分配的活性与期限规则。修复为 touch 也受 maxRenewalsWithoutProgress 限制、到期按宽限回收。

即：touch 不是无条件的"我还活着"；同会话不构成活性证明；若执行权已回收并产生新 token，旧执行器不得复活，必须重新 claim。跨进程锁协议是另一个独立问题。

## Q13

结论：设置 requiresAudit: true（单档审计门）；agent 不能关，human 是唯一能关门的人。

理由：E02 的落地——单档审计门，requiresHumanReview / gate:human 直接表示"第三方审计门"，wire 名保留、显示迁移（2026-11-02 22:19 拍板"旧门直接降级，做显示迁移"）。实现为 lib/core/audit.js，决策见 docs/decisions/product-policy-review-v6.md。

边界：agent 只能在非 review 状态下开启门，review 状态下 agent 不得开关门；第三方审计可由 agent 出具报告（人可以是 agent），但 audit 门的人类关闭权保留；回滚到旧代码按 human-only 处理，已由 agent 审计 done 的任务不回退。

## Q14

结论：实现状态与文档状态不一致：代码已实现，决策文档仍标 Proposed（人审前）。task.interrupt 现在可用，但不能据此说"已通过人审"。

理由：§6 第 1 条明确记录这一不一致——代码已实现（相关实现提交，lib/core/intent.js、test/core/intent-settlement.test.mjs），而 docs/decisions/rfc-3-state-closure.md 仍标 Proposed（人审前）。E05 也提示"文档状态滞后，不能据此说'已通过人审'"。

使用影响：task.interrupt → interrupted → task.reconcile 这条链路是实现事实，可用于处理未知副作用；但引用它作为"已批准设计"时须注明文档仍 Proposed，缺的是人审记录/文档状态更新。

## Q15

结论：不能按任意 asOf 查询历史时刻的任务状态。该项目前没有历史读模型（asOf 查询）。

理由：§8 第 8 条：RFC-1 已 closed，但传统历史读计划随后暂停（history-audit-rollback-layering.md 第 3 行），能力被"历史知识检索"取代；不能把 RFC-1 的关闭写成"已实现"。现行提供的是 search_project_knowledge / read_project_knowledge（检索事件与文档片段），那是"检索到相关记录"，不是"还原某时刻的状态快照"。

不确定的部分：是否有未记录的临时实现我没有证据；按现有材料只能答"没有 asOf 状态查询能力"。要做需明确：事件重放语义、快照边界、以及"检索命中≠约束恢复"（E04）。

## Q16

结论：文档层面已收口，代码整改未确认完成——不能宣称已从 Router/Gate 等非任务节点拆出。

理由：E06 人类第四次强调后，AI 承认实现里确实把 taskProtocol 加到了 Agent、Router、Gate、Join、Human 上，并承认做成"可选"仍然是耦合、之前处理错了（2026-11-13 20:55）；现行 README 写入"通用图是架构硬边界"、docs/node-protocol.md 记录任务协议归任务节点，旧 ADR 中"整条路径参与任务协议"的表述被明确废弃。但记录本身写明"文档收口不代表代码整改完成"。

依据强弱：人类原始表述 + AI 自认 + 现行 README 三方一致（高）；代码是否已删除各节点的 taskProtocol 挂载，材料未给出提交证据。要确认需查当前实现与测试。
