### E01 项目板不持有文档：从"自己持有正文"到"登记外置引用"

- **编号**：E01
- **项目及时间**：项目 P，2026-11-01 15:38–15:52（北京时间）
- **原始问题**：看板的文档功能是"引用外部文件"还是"自己保存正文"？两份内容并存怎么收敛？
- **人类初始理解**：先核实事实——当前文档功能是引用，还是看板自己持有；确认看板持有正文后，关注"两份内容"的最小改造，而不是直接更换架构。
- **AI 初始理解**：以代码与磁盘为证据作答：文档由看板自己持有正文，不是引用外部文件；并指出拷贝式存储的后果：别处原稿的修改不会同步到看板。
- **发生的分歧**：不是事实分歧，是**架构方向分歧**。现状是"看板持有正文"，人类给出的最终形态是项目板不持有文档：文档放在项目工作区自由管理、随项目走并纳入 git，项目板能引用到文档并管理文档现状。
- **关键纠正过程**：人类不否定事实结论，而是用事实否定现状架构；并要求在开源前完成这件事（它影响项目组织，与只服务于项目板的自身状态不同），让 AI 出计划。
- **最终形成的认知**：文档正文归项目工作区（git），看板只保存登记、定位、基线、状态与漂移观测；"引用"与"持有"是两种职责，不能混用。
- **适用范围**：所有"内容会随项目演进"的文档；看板自有状态（任务、计划、事件日志）不受此限——人类明确区分了"文档"与"自身状态"。
- **反例和边界**：内嵌文档在迁移完成前仍按内嵌结构兼容读取（`docs/EXTERNAL-DOCS.md` §1）；迁移是离线 runbook，不改写历史；未留存的外置正文不承诺可重建。
- **当前状态**：已实现（`docs/EXTERNAL-DOCS.md`、`docs/WORKSPACE-DOCUMENTS-CONTRACT.md`）。
- **原始材料引用**：
  1. 2026-11-01 15:38 的会话【转述】：人类先要求核实当前项目的文档功能究竟是引用还是自己持有正文。
  2. 同会话 AI 回复【转述】：核实后确认文档由看板自己持有正文，不是引用外部文件。
  3. 2026-11-01 15:46 的另一会话【转述】：人类描述目标形态——项目板不持有文档，文档在项目工作区自由管理、随项目走并纳入 git，项目板只负责引用和呈现文档现状。
- **证据置信度**：高。事实有代码与磁盘证据，方向有人类原始表述，落地有现行文档与实现。

### E02 旧门"直接降级"：人类用项目阶段事实否决了 AI 的兼容设计

- **编号**：E02
- **项目及时间**：项目 P，2026-11-02 22:19（北京时间）
- **原始问题**：把"必须人审"的门扩展成"必须有第三方审计（人可以是 agent）"时，存量 `gate:human` 任务怎么处理？
- **人类初始理解**：要的是"不再要求必须人审，而是必须有第三方审计"；对存量兼容没有先验要求。
- **AI 初始理解**：自查发现 P0-1（存量门会被静默降级、回滚会误判）后，改成**两档门**并推荐它；同时提出另一选项：把存量 `gate:human` 一次性显式迁移为第三方审计，并承诺不做静默降级。
- **发生的分歧**：AI 把"回滚兼容 / 存量语义不变"当约束；人类认为项目**未发布**，这个约束不成立。
- **关键纠正过程**：人类直接拍板：旧门直接降级，做显示迁移，因为当前项目未发布，要确保发布是干净的。判断依据是项目阶段，不是技术权衡。
- **最终形成的认知**：单档审计门；`requiresHumanReview`/`gate:human` 直接表示"第三方审计门"，wire 名保留、显示迁移；回滚边界写进设计，不承诺双向兼容。
- **适用范围**：未发布、只有本机 store 的项目。若已有外部 v2 store，人类明确"复议条件：若未来出现外部 v2 store，重新评估"。
- **反例和边界**：发布包纯净另立目标（见 §5 第 2 条）；回滚到旧代码按 human-only 处理，已由 agent 审计 done 的任务不回退；review 状态下 agent 不得开关门，human 是唯一能关门的人。
- **当前状态**：已实现（`requiresAudit` / `lib/core/audit.js`）；决策见 `docs/decisions/product-policy-review-v6.md`。
- **原始材料引用**：
  1. 2026-11-02 的会话【转述】：AI 提出两档门（推荐）或把存量 `gate:human` 一次性显式迁移为第三方审计，并承诺不做静默降级。
  2. 同会话 22:19【转述】：人类拍板旧门直接降级、做显示迁移，理由是项目未发布、发布必须干净。
- **证据置信度**：高。两方立场有原始记录，选择理由与项目事实一致。

### E03 项目板的职责边界：诚实记录，不替证据背书

- **编号**：E03
- **项目及时间**：项目 P，2026-11-05 19:03–19:09（北京时间）
- **原始问题**：项目板是否应该主动检查命令/证据的可执行性？Git、worktree 等依赖要不要提供保障？
- **人类初始理解**：先给三条边界，再问系统既有主动检查命令或证据可执行性的能力应如何收敛。
- **AI 初始理解**：材料未明确表达反对；但既有实现确实包含"主动检查命令/证据可执行性"的能力（人类原始表述为"我们存在…"），说明系统此前把"记录"与"核验"混在一起。
- **发生的分歧**：系统能力（能跑命令、能看 git）与产品职责（该不该替证据的正确性负责）边界不清。
- **关键纠正过程**：人类用三条陈述重划边界：①项目板不应对证据的正确性负责，只做诚实记录并识别漂移，因此跑命令不应是任务板的功能；②npm 安装与源码安装应同形态，使用形态只保留 UI 与 agent 工具；③不提供 worktree 等保障，只读 git 作为增强能力，但不能因没有 git 而不可用。
- **最终形成的认知**：记录谁在何时提交了什么、来源、漂移；不判断结论对错，不代跑命令；Git 是只读、可降级的增强；npm 与源码安装同形态。
- **适用范围**：项目板自身的产品职责。开发者仍须跑测试、独立审查、发布门禁——人类在另一会话明确"开发者不豁免"。
- **反例和边界**：auditor 可以自行核验并出报告，但"不自动核验/背书"限定于系统职责；证据漂移可识别，但"未漂移不等于正确"；无 git 时核心流程仍须可用。
- **当前状态**：已实现并写入跨项目文档（项目 A 仓库 `docs/project-board-boundary.md` §1–§3）。
- **原始材料引用**：
  1. 2026-11-05 19:03 的会话【转述】：人类要求项目板不替证据正确性负责，只诚实记录并识别漂移，跑命令不属于任务板功能。
  2. 同会话 19:09【转述】：人类明确不提供 worktree 等保障，只读 git 作为增强，且无 git 时仍须可用。
  3. 2026-11-05 19:27 的跨项目会话【转述】：人类强调两个项目的能力不重合，这是他定的架构边界。
- **证据置信度**：高。原则由人类逐条给出，落地有跨项目文档。

### E04 历史知识检索：检索命中 ≠ 约束恢复

- **编号**：E04
- **项目及时间**：项目 P，2026-11-13 21:11 → 2026-11-14（北京时间）
- **原始问题**：新会话缺少历史上下文时，能否通过任务板快速恢复"历史决策、设计边界、有效约束及其证据"？
- **人类初始理解**：明确不要"让 Agent 阅读全部历史"，而要以尽可能低的时间、Token 和维护成本，获取足以正确执行当前任务的关键上下文；并要求区分历史讨论、正式决策、有效约束和已废弃方案。
- **AI 初始理解**：先做技术调研（FTS5/BM25/向量/GraphRAG 对比）并提最小方案；对"检索能否替代恢复"持开放态度。
- **发生的分歧**：检索层的"命中条数/相关性"与任务层的"约束是否恢复"不是一回事；冷索引、中文分词、版本噪声会让"零命中"被误读为"不存在"。
- **关键纠正过程**：人类用三次 search-only 实测把问题具体化：冷索引 `indexedThrough=778 / verifiedThrough=2997 / lag=2219`、首次零命中、中文多词零命中、同一任务多版本占据前几条、正文仅观测 96/756；并指出日志追平不等于正文完整覆盖。随后要求首屏折叠同一实体的历史版本、保留旧引用、片段优先给业务原文，并先修续页、条数上限暂时不动。
- **最终形成的认知**：唯一目标是"让新会话恢复足以正确执行的约束"；检索相关性、事实权威性、约束有效性分开表达；检索无命中不等于确认不存在；摘要不能自动晋升为项目事实；检索不得侵入高频写路径。
- **适用范围**：项目 P 历史知识读取与检索；项目 A 负责检索时机与流程门禁，两者职责不重叠。
- **反例和边界**：不引入向量库/GraphRAG/自动权威摘要；不承诺恢复未留存的外置正文；语料只限已有记录与登记文档，不扫描整个工作区；本阶段完成≠已证明能减少错误实现。
- **当前状态**：已实现 `search_project_knowledge`/`read_project_knowledge`（DSH 与 MCP 两端），方向见 `docs/decisions/structured-continuous-knowledge-base.md`；"整体约束恢复效果仍须通过真实任务实验评估"。
- **原始材料引用**：
  1. 2026-11-13 21:11 的 Codex 会话【转述】：人类提出核心问题——新任务、尤其跨会话缺上下文时，能否通过任务板快速恢复相关的历史决策、设计边界、有效约束及证据。
  2. 2026-11-14 16:03 的 Codex 会话【转述】：人类指出日志追平不等于正文完整覆盖，也不能据此证明 read 接口失效。
  3. 同会话人类追问【转述】：是否严格限制了碎片数量、碎片信息是否不足、是否反被 id 与哈希等无关数据占据。
  4. `docs/decisions/structured-continuous-knowledge-base.md`（2026-11-13）【转述】：检索无命中不等于确认不存在约束；生成的摘要不能自动晋升为项目事实。
- **证据置信度**：高（方向与边界）；中（效果）。"检索是否真的减少错误实现"尚无验证证据，文档自己也这么写。

### E05 未知副作用：宁可保留不确定性，也不为了让不变量成立而"结清"

- **编号**：E05
- **项目及时间**：项目 P，2026-10-28 00:14（北京时间；UTC 2026-10-27 16:14）
- **原始问题**：`task.block` 可以在 open intent 未结清时把任务置为 blocked，违反 I6（open intent 只能对应 in_progress/interrupted）。怎么收口？
- **人类初始理解**：这不是状态字段问题，是核心承诺问题；副作用结果不明时必须保留待对账状态。
- **AI 初始理解**：为了让 block 可用，建议在同一 commit 把 intent 标成 `abandoned`（方案 A，推荐）。
- **发生的分歧**：AI 的方案让"不变量成立"，代价是把"可能已发生的副作用"标成"这次尝试停止"；人类认为这等于把不确定性藏起来。
- **关键纠正过程**：人类给出判据：副作用结果不明必须走 interrupted/reconcile，不能借 block 清掉待对账状态；并补原则：这是核心承诺问题，不只是状态字段怎么收口；宁可保留不确定性，也不能为了满足 I6 把不确定性藏起来。随后要求先不动手，只冻结口径。
- **最终形成的认知**：open intent 是 WAL，不是普通状态字段；关闭必须带结算记录；结果不明时 block 拒绝，走 `task.interrupt` → `interrupted` → `task.reconcile`；`abandoned` 只表示"这次尝试停止"，不表示没有副作用。
- **适用范围**：所有"副作用可能已发生但结果未知"的状态收口，包括 release/cancel/override（reject 做防御性同规则）。
- **反例和边界**：`unblock` 不重建 intent，回到 in_progress 后必须重新 begin；abandoned 必须带 closeReason/outcome/sideEffects/actor/at。
- **当前状态**：已实现（相关实现提交，`lib/core/intent.js`、`test/core/intent-settlement.test.mjs`）；但决策文档 `docs/decisions/rfc-3-state-closure.md` 头部仍标 **Proposed（人审前）**——文档状态滞后，不能据此说"已通过人审"。
- **原始材料引用**：

### E14 追溯与拦截分属两侧：对人不设死路，对 AI 必须拦截

- **编号**：E14
- **项目及时间**：项目 P，2026-11-01 22:40（北京时间；会话起于 10-28）
- **原始问题**：验收/漂移的严格度应该由系统定，还是由项目所有者定？
- **人类初始理解**：安全感由可追溯提供，而不是拦截提供；人应当对自己项目的严格程度负责，有时候过多限制是不好的。
- **AI 初始理解**：材料未明确表达相反立场；但人类随后补了一句限定，说明 AI 当时把原则理解成"对所有角色都放宽"的风险是真实存在的。
- **发生的分歧**："可追溯优先"是否意味着对 AI 也放宽拦截。
- **关键纠正过程**：人类立即补充：这是对人说的，AI 确实得拦截。AI 据此把原则写成两侧：AI 侧保留完整性拦截与"不能自证完成"，人侧保留可追溯 + 合法出路。
- **最终形成的认知**：P4.2 分两侧——AI（worker）必须拦截（submit/reconcile 前完整性错误与漂移直接打回，verify 非 human 不可）；人（owner/verifier）不以死路拦截，严格度可声明、可审计、可回退；每个阻断都要留记录并给至少一条非豁免出路。
- **适用范围**：验收、漂移豁免、阻断设计。
- **反例和边界**：硬底线只保留"记录会失真"的完整性问题（missing/unreadable、command 失败、proof 错绑、路径逃逸）；新鲜度与严格度属于 owner 选择。
- **当前状态**：已写入 `DESIGN.md` P4.2。
- **原始材料引用**：
  1. 2026-11-01 22:40 的会话【转述】：人类提出安全感由可追溯而非拦截提供，人对自己项目的严格程度负责，过多限制并不好。
  2. 同会话同一分钟【转述】：人类补充这句是对人说的，AI 确实需要拦截。
- **证据置信度**：高。原则与其适用范围由人类在同一分钟内补齐。

### E15 把人类的"10 左右"当成设计目标：Flow 视图的数量假设

- **编号**：E15
- **项目及时间**：项目 P，2026-11-07 02:19–02:21（北京时间；UTC 2026-11-06 18:19）
- **原始问题**：单人 + AI 场景下，进行中/review 的任务在视图里该展示多少？
- **人类初始理解**：先给运行事实——多数时候需要人看且并行的可能是 10 个左右，20+ 也不是没可能；这是**规模上限**，不是"要全显"。
- **AI 初始理解**：把"10"当成设计点：认为 10 就是主设计点，≤10 不该出现展开/滚动，10 张本来就该一屏看全，出现折叠反而是设计失败。
- **发生的分歧**：人类说的是"可能有多少"，AI 听成了"界面上要放多少"。
- **关键纠正过程**：人类反问 10 全量是不是有点多，说实话 10 可能还真不一定要看，最多展示 3–4 个；AI 承认上一轮被"10"带偏，10 张里真正需要盯着看的本来只有 1–3 张。
- **最终形成的认知**：默认有界预览——正在推进最多 3 张、需要处理最多 2 张；计数打开浮层看全量；主路径不滚动；卡片不挂 worktree/分支/commit；并发数与常驻占位解耦。
- **适用范围**：单人 + AI 的推进视图/首屏。多人团队或评审集中期不适用。
- **反例和边界**：隐藏可以，隐藏信号不行——溢出条必须带异常汇总；10 张以上本身是注意力超配信号，不是正常态。
- **当前状态**：已实现为可切换视图（`?view=flow`），默认仍看板；3/2 上限写入 `docs/design/flow-view.md` §4.1（"3–4 自适应"方案被后续修订为 3/2）。
- **原始材料引用**：
  1. 2026-11-07 02:19 的会话【转述】：人类给出规模上限：需要人看且并行的通常约 10 个，20+ 也可能，但这种场景往往不需要人一直盯着。
  2. 同会话 02:20【转述】：AI 把 10 当成主设计点，主张一屏看全、不要折叠。
  3. 同会话 02:21【转述】：人类反问 10 全量是否太多，建议最多展示 3–4 个。
  4. 同会话【转述】：AI 承认被"10"带偏。
- **证据置信度**：高。误解与纠正在一分钟内完成，原始记录完整；最终上限有现行设计文档。

### E16 租约活性：同会话可续租，但旧执行器不能靠 touch/renew 复活

- **编号**：E16
- **项目及时间**：项目 P，2026-10-28 00:02 → 13:05（北京时间）
- **原始问题**：租约 TTL 过期后，同会话 owner 能不能"无痛续租"？`touch`/`renew` 与租约活性是什么关系？
- **人类初始理解**：同会话续租可以支持，但必须有明确的活性判据或有限宽限期；执行权被回收、产生新 token 后，旧执行器绝不能复活。
- **AI 初始理解**：把"同会话"当充分条件——认为 TTL 过期后 owner 同会话可无痛续租。
- **发生的分歧**：同会话不等于仍然活着；"能续租"与"执行权归属"是两件事。
- **关键纠正过程**：人类先给判据，后在实证中进一步收紧（显式 renew 虽返回拒绝，租约事实上已经延长），要求统一 touch、renew、自动重新分配的活性与期限规则；AI 修复为 `touch` 也受 `maxRenewalsWithoutProgress` 限制，租约到期后按宽限回收。
- **最终形成的认知**：活性判据统一到租约 + fencing token；宽限期有限；旧 token 不得复活；续租次数受"无进展"约束。
- **适用范围**：单进程/跨进程的租约与恢复。跨进程锁协议是另一个独立问题（当时未完成）。
- **反例和边界**：`touch` 不是无条件的"我还活着"；宽限期不是永久保留；副本/分身不在此保证内。
- **当前状态**：已实现并写入 RFC-3 §9（S4 租约活性约束）；相关修复提交。
- **原始材料引用**：
  1. 2026-10-28 00:02 的会话【转述】：AI 提出 TTL 过期后同会话 owner 可无痛续租。
  2. 同会话 00:14【转述】：人类要求同会话续租必须有明确活性判据或有限宽限期。
  3. 同会话 13:05【转述】：人类实证指出显式 renew 虽返回拒绝，租约事实上已被延长。
- **证据置信度**：高。两方原始记录 + 修复报告可查；"binding=活性"这一等式 AI 并未明确主张，不能归为它的立场。

### E17 "帮我分析"被扩成"做评估"：AI 的范围越界

- **编号**：E17
- **项目及时间**：项目 P，2026-11-08 00:00（北京时间；UTC 2026-11-07 16:00）
- **原始问题**：人类想自己读后端代码，让 AI 引导梳理架构与入口。
- **人类初始理解**：要的是"分析"——按需展开、记录坏味道，供人类自己判断。
- **AI 初始理解**：把"分析"扩成"评估"，自行新增 R03 等评估条目，并输出评估结论。
- **发生的分歧**：人类只要分析材料，AI 交付了评估判断；范围与产物类型都不对。
- **关键纠正过程**：人类直接指出从 R03 开始都不是自己要求的，不是让 AI 做评估，只需帮助分析；同时给出处置：一项不管、一项记为一个坏味道。AI 承认越界，把辅助读代码变成了自行评估和立项，并撤下未经要求的评估条目。
- **最终形成的认知**：辅助读代码时，产物是"可核对的分析与坏味道记录"，不是"评估结论"；是否升级为评估由人类决定。
- **适用范围**：人类主导的代码阅读/架构梳理。若人类明确说"做评估"，不受此限。
- **反例和边界**：同一会话后段人类主动要求做专项审查并先定审查目标——人类要评估时会自己开口；边界在于"不要替人类决定产物类型"。
- **当前状态**：当轮已撤项；未形成书面规范，属会话内约定。
- **原始材料引用**：
  1. 2026-11-08 00:00 的会话【转述】：人类指出 R03 起不是自己要求的，不是让 AI 做评估，只需帮助分析，并给出两项处置。
  2. 同会话 AI 回复【转述】：AI 承认越界，把辅助读代码变成自行评估和立项。
- **证据置信度**：高。人类原始表述与 AI 自认都在同一会话内。

### E18 能重放不等于语义兼容

- **编号**：E18
- **项目及时间**：项目 P，2026-10-28 20:06–20:11（北京时间）
- **原始问题**：如何保证发布不会让旧代码读新日志时出错？
- **人类初始理解**：需要真实的兼容回归，不只是"能打开日志"。
- **AI 初始理解**：主张新事件类型必须 no-op——旧代码忽略未知事件即可视为兼容。
- **发生的分歧**：能重放/能打开，是否足以证明语义兼容。
- **关键纠正过程**：人类用反例直接否定：旧代码忽略新事件，不等于向后兼容。AI 接受，并把兼容拆成按语义分类（applied/additive/migration/refuse）；例外是"新事件在同一 commit 携带完整状态"时才可安全忽略。
- **最终形成的认知**：兼容性按语义分类，未知事件默认拒绝；能打开日志不等于语义兼容；破坏性迁移需要双读窗口或备份回滚。
- **适用范围**：事件日志、发布门与回滚。
- **反例和边界**：`meta-edited`/`assignment` 等事件在同 commit 有完整状态伴随时可安全 additive；直接对存量未知事件 fail-closed 会锁死项目，需要可回退的处理方式。
- **当前状态**：已实现（`EVENT_REGISTRY` 分类 + 兼容测试）。
- **原始材料引用**：
  1. 2026-10-28 20:06 的会话【转述】：AI 提出新事件类型必须 no-op，作为反向兼容测试要求。
  2. 同会话 20:11【转述】：人类指出旧代码忽略新事件不等于向后兼容。
- **证据置信度**：高。纠正与原始记录俱在。

### E19 驳回/重做不换委派人：从"体验不合理"到"实现违反设计不变量"

- **编号**：E19
- **项目及时间**：项目 P，2026-10-22 20:48（北京时间）
- **原始问题**：任务被驳回/重做后直接回到 ready、委派人丢失，是否合理？接手/交接有没有审计？
- **人类初始理解**：来自使用体验——驳回、重做会直接回就绪，感觉不合理；理想是不换委派人继续，除非另有所指；同时怀疑任务缺乏接手、交接相关审计。
- **AI 初始理解**：按"体验优化"盘点现状，先给现状清单，未预设这是缺陷。
- **发生的分歧**：人类的"感觉"是产品判断；需要确认它是不是真问题、根因在哪。
- **关键纠正过程**：AI 用代码与探针把"感觉"升级为"必然"：submit 已删租约、清 owner，reject 只看有没有租约，所以永远走 ready 分支；并指出实现与设计 T11 不符，按缺陷修。
- **最终形成的认知**：驳回/重做保留委派人；接手/交接要有归属链审计；未就绪任务要能看到前置依赖。三者落成任务（T1–T7）。
- **适用范围**：任务流转与审计。依赖"任务在 review 时没有负责人"这一实现事实，不是通用产品原则。
- **反例和边界**：换人仍需显式 release/claim；"交接"是新增动作，不是把 release+claim 隐式合并；review 状态任务无 owner 的问题被单列。
- **当前状态**：已实现（相关实现提交）；方案见 `docs/design/reject-redo-preserve-assignee.md`。
- **原始材料引用**：
  1. 2026-10-22 20:48 的会话【转述】：人类提出驳回、重做直接回就绪不合理，理想是不换委派人继续；并怀疑缺少接手/交接审计。
  2. 同会话 AI 盘点【转述】：AI 用代码确认驳回回就绪不是感觉而是必然，并指出实现与设计不符。
- **证据置信度**：高。人类原始表述、AI 根因、设计文档与提交均可核对。

## 4. 重复或高度相似的事件

1. **E02 / E09 同属一次会话的连续决策**（审查治理 v6）：E02 是"要不要兼容"，E09 是"原则适用于谁"。共享同一历史前提（项目未发布），做实验时应作为一组，避免把"未发布"重复计分。
2. **E10 / E15 / E17 是同一失效模式的三次发作**：把人类话语中的一个局部信息（"注解"、"10 左右"、"分析"）扩张成产物类型或设计目标。建议作为一个"范围/语义扩张"因子的三个实例，而不是三个独立机制。
3. **E01 与 E03 都涉及"项目板该持有什么"**，但对象不同（文档正文 vs 证据正确性），边界相反（不要持有 vs 不要背书），可做对照题。
4. **E05 与 E16 同属"不确定状态不能假装确定"**：E05 是副作用，E16 是租约活性。可作为同一上位原则的两个实例。
5. **E11 与 E08 都关于"记录/事实不可削减"**：E08 是目的层，E11 是分层（判定可轻、记录不可轻）。有重叠，但证据链独立。

## 5. 缺少证据的事件

1. **"AI 删断言/放宽输出来让门禁变绿"**：2026-11-08 人类确实要求保证修复不只是改输出，但 2026-11-09 一份独立审计（本机归档）结论相反——断言 4814→4843（+29）、skip 13→13、95 个旧测试中 92 个 blob 不变。**该怀疑被证伪**，不能写成 AI 曾经作弊；可写"人类预设了这种失败模式并做了防御"。
2. **发布包纯净（显示迁移 ≠ npm 包零旧名）**：2026-11-02 人类先问能否确保发布版纯净，AI 答按当前设计发布包做不到字面零旧名，随后人类接受将其明确为技术债。材料完整，但它更像 E02 的后续细化，未单列事件；落地有 `scripts/check-release-purity.mjs`。
3. **Flow "3–4 自适应"**：会话中曾定"1440 宽 3 张、2309 宽 4 张"，现行设计已改为固定 3/2；属同一事件的中间版本，不单列。
4. **计划级验收（任务 done ≠ 计划达标；第三方报告 + 人裁决）**：2026-10-23 人类提出并让 AI 建计划（第三方 agent 出报告 + 人裁决），但现行 docs 中找不到对应设计或实现；只在会话里出现，**不能算已形成机制**。
5. **人类的"验收瓶颈"**：2026-11-05 人类说"目前我的验收瓶颈太严重"，后续只看到"不逐任务验收"的临时缓解，没有形成机制。
6. **"看板 done 与 master 代码不一致"**：11-01 的会话里 AI 说看板上的 done 与 master 代码不一致，但同条也承认可能按分支验收；材料未记载逐任务对账结论，不能认定验收造假或任务未完成。
7. **"AI 把记录真相视为退化"** 之外的同类归因（如"AI 主张无限穷尽"）：子代理初判后被其自行撤回，未找到原始记录，不采用。

## 7. 最值得优先转化为实验探针的事件

建议优先 5 个，按"默认答案容易错 + 有项目特有理由 + 可判分"排序：

1. **E03 职责边界（诚实记录 ≠ 替证据背书）**
   - 为什么：最反直觉的项目原则；新会话很容易把"证据"扩成"核验证据正确性"。
   - 可检验：给"看板是否应该跑命令验证证据"的场景，看它是否引入执行/背书职责；能否说出"漂移可识别，但未漂移不等于正确"。
2. **E01 文档外置（持有 → 引用）**
   - 为什么：模型默认按"文档管理"直觉答"存在看板里"；正确答案依赖"文档随项目走、上 git"的项目事实。
   - 可检验：给现状（看板持有正文、两份内容）问最终形态；看是否答"外置 + 登记/基线/漂移"，而不是"同步两份"。
3. **E02 旧门降级（未发布 → 不做兼容）**
   - 为什么：默认工程直觉是"保留旧语义、加开关"；正确答案依赖"项目未发布、无外部 store"这一历史状态。
   - 可检验：给"已有 v2 数据、尚未发布"的设定，问要不要两档门；看是否能引用阶段事实否决兼容成本。
4. **E10 TS=注解（类型说明 ≠ 写注解）**
   - 为什么：语义型误解，跨模型可复现；"当作注解"本身有歧义。
   - 可检验：给出"把 TS 当作以前的注解、只是用 TS 表示"这一表述，问下一步该产出什么；看是否落到 JSDoc/注解层。
5. **E04 检索≠恢复（命中不等于约束有效）**
   - 为什么：与 Converge 主题同一；模型天然把"检索到"当成"恢复到了"。
   - 可检验：给一组检索结果（含旧版本、零命中、正文缺失），问"能否据此认定约束存在/不存在"；看是否区分相关性、权威性、有效性。

次优但值得保留：E05（未知副作用）、E06（通用图）、E07（架构缺陷定级）、E17（分析→评估，行为型）、E15（数量假设）。
