# 认知树 MVP：总架构

**先分清两个内核。** 业务内核回答“这是谁提出的判断、为什么保留或排除、谁确认”；UI 内核回答“人现在在读哪个问题、要看哪条依据、如何纠正”。两者都不把 DSH 当作运行前提。图中包含两种环境：独立网页在页内装配正式内核；DSH 插件在隔离工作区接入 SQLite，安装到正在使用的 profile 另行授权。独立网页和隔离验证都不能代替上线后的宿主验收。目录定位看[结构图与放置判据](<STRUCTURE.md>)，已拍板的语义看[人的决定](<PRINCIPLES.md>)。

## 一、总图：同一棵树，两种入口

![总架构：DSH 与独立浏览器复用 UI 和业务内核，MCP 并列预留](<diagrams/overall.svg>)

[独立看总图](<diagrams/overall.svg>) · [图源](<diagrams/overall.mmd>)

| 环境 | 人与 AI 从哪进 | 正文在哪里 | 换掉环境时不改什么 |
| --- | --- | --- | --- |
| DSH（首版） | 人从侧栏主面板或聊天中的提议卡进入；AI 从 DSH 工具进入 | 服务端适配器在所属工作区的 `.converge/` 持久化 | 同一套树规则、读写用例、UI 组件 |
| 独立浏览器（首版） | 独立网页挂载同一个应用壳；开发模拟器扮演 AI，真实的人仍在页面确认 | 本地测试存储与 DSH 数据隔离；业务内核可在页内运行 | 不模拟树规则，不需要 DSH 或一个常驻后端 |
| MCP / 其他环境（未来） | 从新适配器调用同一操作目录；不经 DSH 插件转发 | 由新装配选择存储及同一权威写入口 | 不向业务内核加入 MCP SDK、连接或宿主分支 |

**复用的是语义，不是权限。** 操作目录（catalog）声明一项操作做什么、接收什么，以及允许的 actor；各入口按能力映射适当子集，不必暴露全部操作。DSH 的面板请求和工具调用可以传不同格式，却不能各实现一遍“剪枝”。看板只记录这个工程的开发事实，不是认知树的数据库或运行依赖。

## 二、后端图：规则、写入和 I/O 的边界

![后端：适配器翻译，操作目录分派，模型提交，存储端口隔离 I/O](<diagrams/backend.svg>)

[独立看后端图](<diagrams/backend.svg>) · [图源](<diagrams/backend.mmd>)

**写路径**：入口识别调用方 → catalog 分派 → models 开单树事务 → commands 依据相关节点决定本次变更 → operations 给出新增分支、状态与日志的变更集 → TreeStore 提交。模型是唯一提交方，只写本次涉及的数据。保存失败时回滚，不向 UI 报「已确认」。见[内核接口单](<design/kernel-interfaces.md>)。

**读路径**：入口 → catalog → queries 经 TreeStore 打开一致读快照，依参数按批取子节点、引用邻居和必要父链。返回保留原父子关系的局部树，引用作旁边的关联；预算在哪里停止就在哪里标明，不先读整树再裁剪。节点正文和修订时间线按需读。展开不反写，事实冲突只标记而不自动裁定。

**源码依赖与调用区别**：kernel 声明 TreeStore、Clock，装配提供实现。运行中的模型会调用存储端口，但 `kernel` 不 import 文件系统、浏览器存储、DSH、React 或 MCP。DSH 服务端负责路由、工具注册、工作区定位和文件 I/O；不把全局 DSH 会话对象传入领域规则。

## 三、前端图：展示、交互与环境

![前端：DSH 与浏览器分别接线，共用 React 18 视图、模型和端口](<diagrams/frontend.svg>)

[独立看前端图](<diagrams/frontend.svg>) · [图源](<diagrams/frontend.mmd>)

- **ui**：React 18 应用壳组合功能模块；模块把点击、编辑等手势翻译为意图。UI 模型持有选中节点、展开状态和未提交的输入。树正文来自读投影，不另养一棵可以独立确认/剪枝的树。认知交互走 CognitionClient，宿主导航等环境能力走 HostBridge；UI 不直接发 HTTP 或读宿主全局量。
- **DSH 客户端**：以宿主的 React 实例挂载应用；插件槽位（如 main、sidebar.panellist、tool.call.toolview）负责入口，不成为 UI 内核 API。与服务端的同源 HTTP、宿主导航及挂卸载由适配层处理。面板和卡片对同一提议的操作进入同一用例，不能因为有两种入口就产生两套事实。
- **独立网页**：自带 React；由本地 client 连接真实内核、浏览器测试存储和示例数据。模拟器只制造 AI 输入，不生成“人确认”；浏览器能跑通不能代替 DSH 插件验收。

**设计验收场景，而非预定页面布局：**以 T1 的“为什么不用纯树”为例。人应能从问题顺着树走到被剪的方案，看到剪除理由、复活条件和关联实例；切换到“树 + 有类型引用边”时不会丢失刚才的位置。分支状态与确认来源应同时可读，不仅靠颜色。跨引用按需出现，不用满屏连线；空、加载、失败和未保存反馈也属于体验。大纲还是空间树图、如何排布检查器，由人看过可点原型再定。

## 四、走一次变更到确认

```text
AI 模拟器 → AI 入口 → catalog → 新增同级替代候选，保存即生效，旧判断未动
人或 AI → 执行替代 → 同一事务：候选记为已执行、旧判断剪除、追加形成记录
人的阅读栏 → readNode → 读到实际变更与修订 ID → 人明确 confirm 指定目标
                                   → 仅标记仍指向该记录的节点，另记人确认
```

1. 补充、勘误挂在原节点下；替代候选与旧判断同级。人和 AI 的日常写入都先标未确认。执行者是人也不等于已经确认，AI 传入 `human` 字段更不能替人确认。
2. 执行替代保留旧正文、引用、剪除理由、复活条件和新旧关联。它与「确认这次执行」是两笔不同意图的事务；确认本身不改变分支状态、不造节点。若一侧后来又变化，不能替新变更背书。见[人的决定](<PRINCIPLES.md>)。
3. 在时间线上能查回为什么排除、谁何时确认。展开、折叠和浏览不生成形成记录。

## 五、如何验证这个设计（实现阶段）

| 设计承诺 | 应当取得的证据 | 不能据此声称 |
| --- | --- | --- |
| 内核独立运行 | ES-only 的 TypeScript 配置（无 DOM/Node 环境类型）与包依赖核对；Vitest 以内存 TreeStore、可控时钟执行真实用例，不启动 DSH | tsc 通过本身不能排除经包或声明引入宿主；单测不能证明接入 |
| 同一用例不因入口改变 | 对 DSH 翻译与 browser local client 喂同一种意图，比较判断状态、来源及错误；AI 入口不能确认，人入口不能绕开规则 | 模拟器不是 DSH agent，测试数据不是正式树 |
| UI 可独立评审、DSH 可直接使用 | 独立网页由人走完阅读与纠偏；DSH 阶段另以真实侧栏/卡片和工具走同一场景，记录影响面和本机观察 | 不用截图、图稿或局部成功宣称真实插件已交付或普遍无性能影响 |

**扩展时的两个问题：**只是换入口/存储？实现端口并在新适配器接线。真的增加树的能力？先确认其领域语义（例如一种新边回答哪个现有结构无法回答的问题），再改目录和模型，并让各入口按其权限映射。首版不为假想宿主建插件平台。
